4. WebRTC Peer-to-Peer Video & Real-Time Signaling

WebRTC creates a direct, peer-to-peer audio/video tunnel between Patient and Doctor using the browser's native media engine:

Step-by-Step Signaling Handshake:

  1. Room Join: Patient and Doctor connect via Socket.io to join-room { roomId }.
  2. Offer Creation: The first peer calls pc.createOffer() and emits webrtc-offer over Socket.io.
  3. Answer Generation: The receiving peer calls pc.setRemoteDescription(offer), calls pc.createAnswer(), and replies with webrtc-answer.
  4. NAT Traversal (STUN): Both browsers query Google STUN servers (stun:stun.l.google.com:19302) to discover public IP/port candidates and exchange them via webrtc-candidate.
  5. Direct Media Stream: Once candidates match, high-definition 1080p video streams directly peer-to-peer with 256-bit DTLS/SRTP encryption.

5. AI Clinical Triage & Safety Fallback Engine

The AI engine translates raw, unstructured patient text into structured medical recommendations:

1. Gemini 2.0 JSON-Schema Prompting: Enforces exact JSON keys: summary, suggestedSpecialty, urgencyLevel, recommendedAction, and keyQuestions.

6. Key Engineering Challenges & Solutions

Challenge Root Cause Implemented Solution
WebRTC Race Conditions Remote peer received ICE candidates before initializing RTCPeerConnection. Implemented stateful sequencing in VideoConsultationPage.jsx: connection is created upon user-joined and candidates are buffered until remote description is set.
Concurrent Booking Collisions Two patients booking the same slot at the exact same millisecond. Enforced composite database index { doctor, date, timeSlot } + atomic recycling of cancelled slot records.
Password Token Security Leaks Initial API returning reset tokens in HTTP response bodies. Hashed tokens with SHA-256 in MongoDB (+1 hour expiry) and delivered tokens strictly via verified SMTP email.
Zero-Downtime Resilience Cloud DB cold-starts causing evaluation failures. Integrated an in-memory data store fallback in server.js routing traffic seamlessly when database is unreachable.

7. Senior-Level Interview Preparation Master Guide

Q1: How does WebRTC connect two users across firewalls and NATs?
WebRTC uses Session Description Protocol (SDP) and ICE. Our Socket.io server acts as the signaling channel. Peers exchange SDP Offers and Answers. Simultaneously, STUN servers resolve the public IP/port mappings (NAT traversal). Once candidates match, an encrypted P2P media stream is established directly between browsers.
Q2: Why use WebSockets alongside REST APIs instead of WebSockets for everything?
REST APIs are ideal for idempotent CRUD operations (authentication, profile updates, medical records) where HTTP caching, status codes (200, 401, 500), and rate-limiting middleware provide security. Socket.io is used specifically for high-frequency real-time events: WebRTC signaling, in-call chat, and instant dashboard push notifications.
Q3: How is Role-Based Access Control (RBAC) enforced in the backend?
We enforce defense-in-depth security: protect middleware validates the JWT token signature and decodes user context. authorize('DOCTOR', 'ADMIN') checks permissions. In controllers, we enforce object-level ownership (e.g., doctors can only prescribe for appointments they attend; patients cannot modify appointment statuses).
Q4: How would you scale this platform to 100,000 concurrent video calls?
1) Transition from mesh P2P to a Selective Forwarding Unit (SFU) like Mediasoup or LiveKit to optimize client bandwidth.
2) Implement a Redis Adapter for Socket.io to scale WebSocket servers horizontally behind an NGINX load balancer.
3) Shard MongoDB by doctorId and date with Redis caching for doctor directories.
